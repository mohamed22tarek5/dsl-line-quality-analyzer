## ℹ️ INFO — معلومات عن المشروع

### ما هو هذا المشروع؟

مجموعة **برومبتات هندسية جاهزة** تحوّل أي مساعد ذكاء اصطناعي (ChatGPT / Claude / Gemini / Copilot / DeepSeek) إلى **مهندس شبكات متخصص** يحلل قراءات خط الإنترنت الحقيقية من الراوتر أو جهاز ONT — بدل الاعتماد على Speedtest فقط الذي لا يكشف جودة السلك أو الفايبر.

لا يوجد كود ولا تثبيت ولا برامج. المشروع كله ملفات نصية `*.md`:

- تنسخ البرومبت المناسب كاملاً.
- تلصقه في الشات.
- ترفع Screenshot أو تلصق القيم كنص.
- تقرأ تقريراً هندسياً منظماً.

### لماذا وُجد المشروع؟

لأن شكاوى الإنترنت الشائعة — *"النت بطيء"، "البينج عالٍ"، "الخط بيفصل"، "الدعم يقول الخط تمام"* — لا يمكن حسمها بدون قراءة **بيانات الخط الفعلية**: Sync و Attainable و SNR و Attenuation و CRC/FEC و Uptime (للنحاس)، أو TX/RX و Voltage/Bias/Temp و OLT/PON (للفايبر). هذه البرومبتات تستخرج هذه القيم بدقة وتربطها ببعضها وتمنع التخمين.

## 💡 HOW IT HELPS — كيف يساعدك؟

### هل تعاني من هذه المشاكل؟

- الإنترنت بطيء رغم أن الباقة كبيرة؟
- Ping عالٍ أو غير مستقر في الألعاب؟
- لمبة DSL/LOS تفصل أو ترمش كثيراً؟
- تريد تعرف هل خطك يستحمل سرعة أعلى قبل ما تكلم الشركة؟
- الدعم الفني يقول "الخط تمام" وأنت ما زلت تعاني؟
- Speedtest ممتاز أحياناً وسيئ أحياناً ولا تعرف السبب؟
- فايبر جديد ولا تعرف هل الإشارة الضوئية سليمة أم التركيب فيه مشكلة؟

**هذا المشروع يعطيك تحليلاً هندسياً بالأرقام والدليل** لتتكلم مع الشركة بلغة تقنية بدل "النت بطيء".

### لمن هذه الأدوات؟ وكيف تساعد كل فئة؟

| الفئة | كيف تستفيد؟ |
|---|---|
| **المستخدم المنزلي** | يفهم حالة خطه بلغة مبسطة + يعرف هل سرعته الحالية ملائمة للاستقرار + يعرف أهم خطوة تالية بالترتيب + يفرّق هل المشكلة DSL/فايبر أم Wi-Fi/جهاز. |
| **الجيمر وصاحب البث** | يفصل مشكلة Ping/Bufferbloat عن ضعف الإشارة + يعرف هل Interleaving/G.INP أو الازدحام هو السبب + يختبر بكابل بطريقة صحيحة. |
| **الفني / مهندس الشبكات** | تقرير منظم وسريع لتشخيص خط العميل + حسابات جاهزة (% استخدام / Headroom / CRC per hour / نسب تحقيق الباقة) + مقارنة قبل/بعد الإصلاح (V2.0 و FTTH). |
| **موظف الدعم الفني / السنترال** | تحديد هل المشكلة داخلية (RJ11/Splitter/تمديدات/تركيب فايبر) أم خارجية (نحاس/بوكس/كابينة) أم بورت/Profile/OLT + تقرير تصعيد رسمي بالأدلة (V2.0). |
| **أي شخص يتعامل مع ISP** | بدل الشكوى العامة يقول: "الخط يعمل على كذا، والقدرة المتاحة كذا، ومعدل الأخطاء كذا خلال Uptime كذا" — مع طلب فحص محدد. |

### ماذا يفعل عملياً لك؟ (الفوائد المباشرة)

1. **يستخرج القراءات بدقة** من الصورة بدون تخمين، ويكتب `غير واضحة — لا يمكن قراءتها بدقة` عند الحاجة.
2. **يربط القراءات ببعضها** (مثال: SNR مع Sync + Attainable + CRC + Uptime — وليس SNR وحده).
3. **يحسب لك:** نسبة استخدام القدرة، Headroom، معدل CRC في الساعة، نسب تحقيق باقة الفايبر.
4. **يقيّم الجودة** بمقياس ثابت (DSL: Excellent/Good/Acceptable/Needs Investigation — FTTH: 8 مستويات حتى حرج).
5. **يعطي قراراً واحداً واضحاً:** رفع DSL (يمكن تجربة أعلى / الحالية أنسب / بيانات ناقصة) أو حكم FTTH النهائي.
6. **يحدد مصدر المشكلة المحتمل بالأدلة** ودرجة الثقة والاختبار المطلوب لتأكيده.
7. **يرتّب خطوات الإصلاح** (من RJ11 والتركيب الداخلي حتى فحص الزوج/البورت/OLT) + فصل Wi-Fi عن الخط.
8. **يكشف البيانات الناقصة** ويطلب فقط اللازم بسبب تقني واضح.
9. **يحفظ المقارنة:** قراءة سليمة مؤرخة + قراءة العطل = تشخيص أدق بكثير (مدعوم بقوة في V2.0 و FTTH).

### الخطوة 3 — أرسل البيانات

- **صورة (الأفضل)** أو نص يدوي بنفس المحادثة.

### الخطوة 4 — اقرأ التقرير

- V1.0: جدول تحليل + خلاصة + قرار فني 6 نقاط.
- V2.0: ما سبق + تقارير الوضع المختار + مقارنة قبل/بعد + تقرير ISP.
- FTTH: تقرير A→I + حكم نهائي من 8 مستويات + توصيات بالأولوية.

### الخطوة 5 — تابع عند الحاجة

لو طلب بيانات ناقصة (Uptime / ES/SES / Speedtest سلكي / قراءة بوقت مختلف / Spectrum / موديل+Firmware) أرسلها ليكمل التحليل بدقة.

**💡 نصيحة احترافية:** احتفظ بقراءة سليمة مؤرخة (Screenshot + التاريخ). عند العطل أرسل القديمة + الجديدة معاً — المقارنة تكشف التدهور أدق بكثير. هذا مهم خاصة لأقسام V2.0 المتقدمة والمقارنة في FTTH.

## 📌 كيف تحصل على البيانات؟ DSL مقابل FTTH

**DSL (V1.0 / V2.0):** المتصفح → `192.168.1.1` (أحياناً `192.168.0.1`/`192.168.8.1` — على ظهر الجهاز) → ابحث عن `DSL / xDSL / VDSL Status / Line Information / Broadband` → قيم `Sync • SNR • Attenuation • CRC • FEC • Uptime • Attainable`.

| الراوتر | المسار التقريبي |
|---|---|
| WE / ZTE / Huawei | `Status → DSL / xDSL` أو `Maintain → DSL Information` |
| TP-Link | `Status → DSL` أو `Advanced → Status → DSL` |
| D-Link | `Status → WAN / DSL Status` |
| ASUS | `System Log → DSL Log` |
| أي VDSL | ابحث عن `Broadband, Line Rate, SNR Margin, Attenuation, DSL Uptime, Counters, Statistics` |

**FTTH:** المتصفح → `192.168.100.1` (صفحة ONT في Huawei/ZTE غالباً) أو `192.168.1.1` (صفحة الراوتر) → ابحث عن `Optical Info / ONT Information / OLT Information / PON Status / Fiber Status` → قيم `TX/RX dBm • Voltage • Bias • Temp • Module • PON Port` **مع المرجعية**. وللسرعة: جهاز واحد بكابل Ethernet مباشرة بدون تحميلات، وسجّل Down/Up/Ping/Loaded/Jitter/السيرفر/نوع الاتصال.

**جودة الصورة = جودة التحليل:** متصفح كمبيوتر + تكبير `Ctrl +` + جدول كامل Down+Up + إخفاء IP/يوزر/باسورد/هاتف/MAC. صور الفايبر: وضّح المسار والانحناءات والتوصيلات ووضع ONT والتهوية — ⚠️ لا تنظر لنهاية الفايبر (ليزر غير مرئي).

## 💡 مثال عملي بالأرقام

### مثال DSL (V1.0 / V2.0)

**أنت ترسل:**

```
Current Down: 40960 kbps / Attainable: 55000 kbps
SNR: 9.2 dB / Attenuation: 14.5 dB / CRC: 120 / Uptime: 48h
```

**المحلل يحسب تلقائياً:**

```
نسبة الاستخدام = 40960 ÷ 55000 × 100 = 74.47%  (Calculation)
Headroom = 55000 − 40960 = 14040 kbps ≈ 14 Mbps  (Calculation)
CRC/hour = 120 ÷ 48 = 2.5 CRC/hour  (Calculation)
```

ثم يفسّر: السرعة أقل من القدرة، الهامش موجود، الأخطاء منخفضة خلال 48h، الاستقرار جيد → التقييم: `السرعة الحالية مناسبة للاستقرار` أو `لا توجد بيانات كافية للحكم` **مع السبب والدليل** (وV2.0 يضيف: مخاطر، سيناريوهات، مقارنة، تقرير ISP).

### مثال FTTH

**أنت ترسل:** صورة Optical (TX/RX + المرجعية) + باقة `200/50 Mbps` + Speedtest سلكي `185/48 Mbps, Ping 8ms`.
**المحلل يحسب:**

```
نسبة تحقيق Down = (185 ÷ 200) × 100 = 92.5%
نسبة تحقيق Up = (48 ÷ 50) × 100 = 96%
```

ثم يقارن TX/RX بالمرجعية + حالة ONT + Loaded Latency/Bufferbloat → يحدد: إشارة أم ONT أم Wi-Fi/Ethernet أم ISP/سيرفر + الحكم والتوصيات.

## 📖 شرح المصطلحات ببساطة

| المصطلح | معناه ببساطة | لماذا يهمك؟ |
|---|---|---|
| **DSL Mode / Profile** | التقنية وإعداد السنترال (مثل VDSL2/17a) | يحدد السرعة القصوى والترددات |
| **Current/Sync Rate** | مزامنة الراوتر↔السنترال (ليست Speedtest) | سرعة الخط الحقيقية |
| **Attainable + Headroom** | قدرة تقديرية + الفارق عن الحالية | هل يوجد مجال نظري لرفع؟ (تقدير وليس وعداً) |
| **SNR Margin (dB)** | هامش الإشارة فوق الضوضاء | رفعه غالباً استقرار أعلى وسرعة أقل — يُقرأ مع الباقي فقط |
| **Attenuation (dB)** | فقد الإشارة في السلك | ظروف انتقال أصعب كلما زاد — لا يُحوَّل لمسافة تلقائياً |
| **CRC / FEC / ES-SES** | أخطاء غير مصححة / مصححة / ثواني أخطاء | تُربط بـ Uptime — الأفضل ES/SES للاستقرار |
| **Interleaving/INP/G.INP/Vectoring** | حماية من الأخطاء والتداخل | استقرار أعلى مقابل Ping أعلى قليلاً — إعداد مقصود غالباً |
| **DSL Uptime** | مدة Sync بدون انقطاع | بدونها لا حكم على الأخطاء |
| **TX/RX dBm (فايبر)** | قدرة إرسال/استقبال ONT الضوئية | تُقارن بمرجعية جهازك — لا تخلط dBm مع dB |
| **ONT (Voltage/Bias/Temp)** | جهد/تيار/حرارة الجهاز | تكشف مشكلة جهاز/تغذية/تهوية |
| **OLT/PON** | السنترال الضوئي والمنفذ والتسجيل | `--` تعني غير معروضة وليست عطلاً |
| **Speedtest/Bufferbloat** | سرعة فعلية + تأخير تحت الضغط | يتأثر بـ Wi-Fi والازدحام والسيرفر — ليس تشخيص خط وحده |

**معادلات DSL:** `% = (Current÷Attainable)×100` — `Headroom = Attainable−Current` — `CRC/hour = CRC÷ساعات Uptime`.
**معادلات FTTH:** `نسبة التحقيق % = (المقاسة÷الباقة)×100` لكل من Down وUp.

## ⚠️ Speedtest ≠ تشخيص الخط

| | Speedtest | بيانات الراوتر/ONT |
|---|---|---|
| يقيس | سرعة فعلية + Ping لجهازك | Sync+SNR+Attenuation+أخطاء+Uptime (DSL) / TX-RX+ONT+OLT (FTTH) |
| يتأثر بـ Wi-Fi؟ | نعم جداً | لا |
| يكشف عطل نحاس/فايبر؟ | لا | نعم |
| يقيّم ملاءمة السرعة؟ | لا | نعم (DSL: Attainable+Headroom / FTTH: الباقة مقابل المقاس) |

**القاعدة الذهبية:** جهاز واحد بكابل Ethernet وبدون تحميلات قبل الحكم، ثم قارن Speedtest مع Sync (DSL) أو مع الباقة (FTTH).

## 🔀 DSL أم Wi-Fi؟ / FTTH أم Wi-Fi؟

| العرض | غالباً خط (DSL/فايبر) | غالباً Wi-Fi/جهاز |
|---|---|---|
| لمبة DSL/LOS تفصل أو ترمش / Sync منخفض / CRC مرتفع / Re-Sync / RX خارج المرجعية | ✅ | ❌ |
| بطء على كل الأجهزة حتى بالكابل | ✅ | ❌ |
| ممتاز بالكابل وسيئ لاسلكياً / Ping عالٍ Wi-Fi فقط | ❌ | ✅ |
| Ping طبيعي خامل ومرتفع تحت الضغط (فايبر) | غالباً Bufferbloat/إدارة — ليست بالضرورة إشارة | — |

V2.0 يفصل 5+ طبقات وFTTH يفصل 10 فئات (ضوئية/تركيب/ONT/OLT/Ethernet/Wi-Fi/راوتر/ISP/سيرفر/نقص بيانات) — بالدليل لا بالتخمين.

**تحسينات بالترتيب (DSL):** فحص RJ11 → Splitter → تجربة Main/Test Point → تقصير كابل DSL → إزالة تمديدات → وصلات → بوكس → زوج نحاسي → بورت/DSLAM → مراجعة Profile. **(فايبر):** مسار/انحناءات/توصيلات → وضع/تهوية ONT → Ethernet سلكي → Wi-Fi → ISP — بدون فتح ONT أو تعديل OLT.

## ⚖️ قواعد الدقة المشتركة

1. **لا تخمين:** الغائب/غير الواضح يُكتب كناقص (`غير واضحة — لا يمكن قراءتها بدقة` / `--` = غير متاحة).
2. **التفريق الدائم:** `Measurement` مقروءة / `Calculation` محسوبة / `Estimate` تقدير / `Interpretation` تفسير.
3. **لا حكم من رقم واحد** (SNR أو CRC أو FEC أو Attainable أو Speedtest وحده).
4. DSL: CRC بالزمن (+ES/SES)، FEC وحده ليس عطلاً، Attainable تقدير chipset، `1dB=72m` تقدير عند الطلب فقط، لا اتهام للشركة ولا تعديل SNR/Profile عشوائياً.
5. FTTH: لا تخلط dBm/dB ولا TX/RX ولا ONT/OLT، المرجعية خاصة بالجهاز، لا تشخيص فايبر من Speedtest فقط.
6. التسلسل: `استخرج → تحقق → احسب → فسّر → اربط → قيّم → حدد الاحتمالات → اقترح → لخّص` — والأولوية **الدقة ثم السبب ثم الحل**.

تقييم ملاءمة سرعة DSL (تقييمان فقط): `السرعة الحالية مناسبة للاستقرار` / `لا توجد بيانات كافية للحكم`.
أحكام FTTH (8): `ممتاز / جيد جداً / جيد / مقبول / يحتاج متابعة / متدهور / حرج / بيانات غير كافية`.
